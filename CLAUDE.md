# AgendaPro — Contexto do Projeto

## O que é

AgendaPro é um produto da **77 IS Tecnologia & Inteligência**, plataforma de agendamento online para barbearias e salões autônomos/pequenos (1 a 5 profissionais). Cliente final agenda sem login via link público/QR Code; dono do negócio tem painel próprio; a 77 IS tem um painel interno de super-admin pra acompanhar novos cadastros e gerenciar trials.

## Stack e workflow (regras fixas)

- **Frontend:** HTML estático + JavaScript puro (ES modules), sem framework
- **Backend/dados:** Firebase Authentication + **Firestore** (migrado do Realtime Database — ver decisão #9)
- **Serverless:** Vercel Functions (`api/*.js`) com Firebase Admin SDK, credenciais via env vars (`FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY`)
- **Hospedagem:** Vercel, deploy automático a partir do GitHub
- **Projeto Firebase:** `agendapro-179cb`
- **URL de produção:** `77-agendapro.vercel.app`
- **Fluxo de trabalho:** git local + Claude Code (migrado de "só GitHub web" em 2026-07)
- **Idioma:** todo o código, comentários e comunicação em português do Brasil

## Decisões de arquitetura importantes

1. **Realtime Database, não Firestore, era a escolha original** — divergência intencional em relação ao BarOS (que usa Firestore); não havia justificativa documentada além de terem sido produtos construídos em momentos/contextos diferentes. Migrado pra Firestore em 2026-08 (ver decisão #9) — agora os 3 produtos da 77 IS seguem o mesmo padrão de banco.
2. **`usuarios/{uid} → { barbeariaId, role }`** — resolve o bootstrapping de autenticação do dono, mesmo padrão do índice `usuarios/{uid} → { orgId }` do BarOS.
3. **`admins77/{uid} → { role: 'super_admin' }`** — separa admin interno da 77 IS (acesso a todos os negócios) do dono de um negócio individual (acesso só ao próprio).
4. **Nunca confiar em dado sensível vindo do navegador em função serverless** — `api/send-notification.js` recebe só `{slug, agendamentoId}` e busca o agendamento real via Admin SDK antes de montar a notificação; não aceita `{token, corpo}` prontos (corrigido em 2026-07 após achado de segurança: o formato antigo permitia qualquer um disparar notificação com texto arbitrário).
5. **`api/agendamentos-ocupados.js`** — o front-end público nunca lê `agendamentos` nem `clientes` completos do Realtime Database (continha nome+WhatsApp de todo mundo, exposto a qualquer visitante). Disponibilidade de horário é calculada a partir desse endpoint, que devolve só `id/profissionalId/dataChave/horario/duracaoMin/status`, sem PII (o `id` foi adicionado depois pra permitir a remarcação ignorar o próprio agendamento no cálculo de conflito).
6. **`api/agendamento-cliente.js`** — autoatendimento do cliente (listar/cancelar/remarcar os próprios agendamentos). O cliente não tem Firebase Auth, então `database.rules.json` bloqueia qualquer escrita dele em um agendamento já existente (só a criação inicial é liberada). Essa função usa o Admin SDK, mas só age depois de confirmar que `agendamento.clienteWhatsapp` bate com o WhatsApp informado — nunca confia em "esse agendamento é meu" vindo pronto do navegador, mesmo padrão da decisão #4. Reaproveita a mesma lógica de disponibilidade de `calcularHorariosDisponiveis` (app.js), portada pro contexto serverless.
7. **Agendamento manual e remarcação pelo dono** (`js/admin.js`) — o dono também consegue criar agendamento direto no painel (antes só o cliente criava pelo link público) e remarcar qualquer agendamento existente. Como o dono já está autenticado e tem os dados completos em memória (`state.agendamentos`), o cálculo de horários disponíveis é feito localmente (`calcularHorariosDisponiveisAdmin`), sem precisar da API pública — mas revalida o slot escolhido no momento de salvar, mesma proteção anti-conflito (corrida entre duas reservas simultâneas) que já existia no fluxo do cliente.
8. **Duas travas de negócio no autoatendimento do cliente, só nele** (`api/agendamento-cliente.js`) — o dono nunca é afetado, remarca/cancela pelo painel sem limite. (a) Cliente só cancela ou remarca até 1 dia (data corrida) antes do agendamento original — depois disso, o botão some da tela e a API também recusa (defesa em profundidade). (b) Cliente só remarca 1 vez por agendamento (`agendamento.remarcacoesCliente`, incrementado só nessa API — remarcação feita pelo dono não conta nem reseta essa contagem). Nos dois casos, quando o limite bate, a orientação é falar direto com o estabelecimento. De brinde, corrigido um bug latente de fuso horário nessa função: o cálculo de "hoje" usava o relógio local do processo Node (UTC na Vercel), mesma classe de bug já corrigida no BarOS — agora usa `Intl.DateTimeFormat` fixado em `America/Sao_Paulo`.

9. **Migração de Realtime Database pra Firestore, replicando o padrão do BarOS e a mesma migração feita no Cardápio Digital.** Motivo: padronizar os 3 produtos da 77 IS no mesmo modelo de banco (Firestore), depois que o Cardápio Digital passou por um bug de `PERMISSION_DENIED` intermitente em escritas sensíveis do CRM direto do navegador — o AgendaPro já não tinha esse problema específico (já usava funções serverless pra tudo sensível), mas ganhou em consistência entre produtos. Decisões:
   - **Schema**: `admins77/{uid}`, `usuarios/{uid}`, `cadastrosAguardando/{slug}` e `logs77/{id}` viraram coleções Firestore quase 1:1. `barbearias/{slug}/info` (que era um sub-nó) virou os próprios campos do documento `barbearias/{slug}` — não precisa mais de sub-nó porque cada doc no Firestore já é sua própria unidade de leitura/segurança. `servicos`, `profissionais`, `clientes` e `agendamentos` continuam sub-coleções, cada doc preservando o mesmo ID que tinha no Realtime Database.
   - **`onValue` → `onSnapshot`** em todo lugar. O painel do dono (`js/admin.js`) tinha 5 listeners separados (info/servicos/profissionais/agendamentos/clientes) — viraram 5 listeners Firestore (1 `onSnapshot(doc)` + 4 `onSnapshot(collection)`), mesma contagem, só a API mudou.
   - **Painel interno 77 IS (`js/painel77.js`) foi redesenhado, não só traduzido.** Antes ele lia a coleção `barbearias` inteira de uma vez, incluindo as sub-coleções de TODOS os negócios (RTDB deixava isso barato; Firestore não tem equivalente). Agora: (a) o listener em tempo real só traz os campos de nível superior de cada negócio (nome/status/trialFim/plano); (b) contagens (agendamentos/serviços/profissionais) vêm de `getCountFromServer()` por negócio, carregadas uma vez ao entrar no painel (`carregarContagens()`) — não em tempo real, já que é um painel de uso ocasional, não um dashboard operacional; (c) o modal "Ver detalhes" de um negócio específico lê a coleção de agendamentos inteira sob demanda (só daquele negócio, só quando o modal abre) — isso continua barato porque é um negócio só, não todos de uma vez.
   - **4 funções serverless (`api/*.js`) traduzidas de `admin.database()` pra `admin.firestore()`** — a lógica de negócio (disponibilidade de horário, fuso horário, travas do autoatendimento do cliente) não mudou, só a forma de ler/escrever.
   - **Identidade do cliente por WhatsApp preservada, não substituída** — `api/agendamento-cliente.js` continua autorizando por comparação de string (WhatsApp enviado vs. `agendamento.clienteWhatsapp`), sem Firebase Auth pro cliente final.
   - **Migração de dados** via `scripts/migrar-rtdb-para-firestore.js` (idempotente) + corte por janela curta de manutenção. RTDB fica dormente por 30 dias após o corte antes de qualquer exclusão.

10. **Rearquitetura de segurança (2026-10): o Firestore não tem mais NENHUMA leitura/escrita pública.** Motivo: auditoria apontou que qualquer usuário logado podia gravar `usuarios/{seu-uid}` apontando pra qualquer negócio e virar "dono" dele (leitura de nome+WhatsApp de todos os clientes, escrita total), que o dono podia editar o próprio `status/plano/trialFim`, e que `agendamentos` aceitava qualquer texto (XSS armazenado no painel + faturamento falsificável + corrida entre dois clientes no mesmo horário). Decisões:
   - **Visitante só fala com `api/*`.** `api/negocio.js` (GET, dados públicos já filtrados: sem comissão, sem tokens, sem PII + ocupação futura), `api/criar-agendamento.js` (POST, **transação**: recalcula preço/duração a partir dos serviços do banco, valida disponibilidade, cria agendamento e atualiza `clientes` atomicamente, notifica o dono), `api/agendamento-cliente.js` (identificar/listar/cancelar/remarcar; remarcar também em transação), `api/cadastrar-negocio.js` (auto-cadastro: o servidor cria negócio + serviços + `usuarios` + fila de aprovação; o negócio SEMPRE nasce em `trial` com 30 dias (`trialFim` definido pelo servidor — o link público já funciona no cadastro, sem aprovação); e-mail vem do token verificado), `api/agendamentos-ocupados.js` (só de hoje em diante).
   - **`api/send-notification.js` foi removido** (endpoint público desnecessário): quem cria o agendamento notifica direto (`api/_lib/notificar.js`; cada aviso tem `tag` única por agendamento e `fcmOptions.link` pro painel, e o service worker só mostra a dele se o Firebase não mostrou a do sistema — antes o dono recebia notificação duplicada). Tokens push saíram do documento do negócio pra `barbearias/{slug}/dispositivos/{deviceId}` (privado; tokens inválidos são apagados no envio).
   - **`firestore.rules` reescrito:** `usuarios` e `barbearias` (create/delete) só via servidor; o dono só atualiza `nome/endereco/telefone/horarioFuncionamento` do próprio negócio (`diff().affectedKeys().hasOnly`); `agendamentos` criado/editado só por dono/super-admin e com forma validada (regex de data/hora, enum de status); `clientes` só dono. `database.rules.json` (RTDB) **não foi alterado** — ver pendências.
   - **Lógica de disponibilidade em um lugar só:** `api/_lib/disponibilidade.js` (`verificarSlot`, função pura). `app.js`/`admin.js` só pintam a grade; quem decide é o servidor. Também exige horário na grade de 30 min, antecedência de 30 min hoje e máximo de 90 dias.
   - **Situação comercial é aplicada:** `api/_lib/negocio.js` (`situacaoNegocio`) — `suspensa` não aceita agendamento; `trial` vencido tem carência de 7 dias (`CARENCIA_TRIAL_DIAS`) e depois fecha; `aguardando_aprovacao` é só legado (cadastros antigos) e segue aceitando. **Fluxo de entrada:** o dono se cadastra → conta + negócio criados na hora com trial de 30 dias → link público já aceita agendamentos. A fila `cadastrosAguardando` virou só um aviso de "novos cadastros" no `/painel77` (conferir/recusar); recusar suspende o negócio. Banner em `admin.js` avisa o dono quando o trial está acabando/acabou ou a conta foi suspensa.
   - **Anti-abuso:** limite de requisições por IP em memória (`api/_lib/http.js`, melhor esforço — cada instância Vercel tem a sua), máx. 5 agendamentos futuros confirmados por WhatsApp/negócio, validação estrita de entradas, respostas de erro sem `err.message`.
   - **Limitação conhecida:** identidade do cliente final continua sendo só o WhatsApp (sem OTP). Código de confirmação por WhatsApp/SMS exige provedor pago — próximo passo de segurança.
   - **Testes:** `npm test` (152 testes, `node:test`, sem dependências) com Firestore falso em memória (`tests/_helpers.js`). `node tests/dev-local.js` sobe o site + APIs com banco falso em `localhost:3000` pra testar o fluxo público no navegador sem tocar em produção. **As regras do Firestore não têm teste automatizado** (o emulador exige Java, não instalado).

11. **Serviços por profissional (2026-10).** Cada serviço pode ser restrito a certos profissionais via `profissionaisIds` (array no documento do serviço). **Ausente ou vazio = qualquer profissional faz** (padrão; serviços antigos não mudam). Regra em dois lugares que precisam ficar iguais: `api/_lib/negocio.js` (`profissionalRealizaServico`, aplicada no servidor em `criar-agendamento` — recusa 409 se o profissional não faz algum serviço) e `js/utils.js` (mesma função, usada pelo link do cliente e pelo painel do dono). No link do cliente, depois de escolher os serviços só aparecem os profissionais que fazem **todos**; o card do serviço mostra "Com X". No painel do dono, o cadastro do serviço tem "Quem realiza este serviço?" — **todos marcados grava lista vazia** (assim um profissional novo entra sozinho nos serviços sem restrição). O agendamento manual do dono também filtra. Remarcar não precisa checar: mantém o mesmo profissional. O vínculo também pode ser feito **no cadastro do profissional** ("Serviços que realiza"): `calcularVinculosProfissional` (`js/utils.js`) calcula quais serviços mudam, o profissional e os serviços são gravados num `writeBatch`, e nunca deixa um serviço sem ninguém que o realize.
12. **Exclusão definitiva de negócio (2026-10).** `api/excluir-negocio.js`, só super-admin (token verificado + `admins77`). Travas validadas no servidor: (a) o negócio precisa estar **suspenso**; (b) é preciso digitar o link (slug) do negócio; (c) nunca apaga o login de super-admin nem de quem está executando. Apaga com `recursiveDelete` o negócio e todas as sub-coleções, a entrada em `cadastrosAguardando`, o vínculo `usuarios/{uid}` e, opcionalmente (padrão marcado no painel), o **login do dono** no Authentication — isso libera o e-mail para um novo cadastro. Registra em `logs77` (`acao: 'excluiu'` + contagens, **sem dados pessoais** de clientes). As regras do Firestore continuam proibindo `delete` de negócios pelo navegador: só o servidor apaga. Validado no Firestore real com negócio descartável (`count()`, `where`, `recursiveDelete`, `deleteUser`).
13. **Visual do serviço (2026-11): foto, ícone ou nada.** Prioridade: **foto > ícone (emoji) > nenhum bloco de ícone** (só nome, tempo e valor). A foto é escolhida no painel, recortada em quadrado 400x400 e comprimida em JPEG **no navegador** (`prepararFotoServico`, `js/admin.js`), e guardada como *data URL* no campo `foto` do próprio serviço — **sem Firebase Storage** (que exige plano pago); limite ~70 mil caracteres. Validador idêntico no navegador (`fotoServicoValida`, `js/utils.js`) e no servidor (`api/_lib/negocio.js`): só JPEG em data URL ≤150 mil caracteres; svg/html/links externos são descartados, porque o valor vira `<img src>`. Ícone: grade de 30 opções + campo "Outro" + "Sem ícone"; `emoji` ausente (serviço antigo) = ✂️, `emoji: ''` = sem ícone; em serviço novo `sugerirEmoji(nome)` sugere pelo nome até a pessoa escolher. Se um dia as fotos pesarem, migrar para Storage (plano pago) ou sub-coleção separada.

As mensagens de erro da ativação agora dizem o motivo (bloqueado, iOS antigo, fora do app...) e cada aparelho é identificado em `dispositivos/{id}.aparelho` ("iPhone · Safari (app)"). (c) **Botão "Enviar notificação de teste"** em Configurações → `api/testar-notificacao.js` (só o dono; limite por usuário; remove tokens vencidos) — use para validar cada aparelho sem fazer agendamento. 15. **Notificação: duplicada no iPhone, toque que abre o agendamento, e horário cancelado que não voltava (2026-11).** (a) O service worker decidia "o Firebase já mostrou?" olhando `timestamp` — o Safari/iPhone não preenche isso, então mostrava uma segunda. Agora compara a **tag da mensagem** (e o `data.FCM_MSG` que o próprio SDK grava na notificação), sem depender de recurso que varia por navegador. Os testes **executam o `firebase-messaging-sw.js` de verdade** num navegador simulado (`carregarSW` em `tests/notificacoes.test.js`). (b) A notificação de agendamento tem `fcmOptions.link = /admin?agendamento=ID`; `admin.js` abre Agenda no dia certo + detalhes (`abrirAgendamentoDaNotificacao`) tanto ao abrir por esse link (painel fechado) quanto por mensagem `notification-clicked` do service worker (painel já aberto — o SDK só foca a janela existente, não navega). (c) Link do cliente: a página guardava a ocupação de quando abriu; agora `app.js` recarrega a ocupação ao ir pra escolha de horário e ao cancelar — antes, um horário cancelado continuava "ocupado" até recarregar a página (no servidor ele já estava livre). (d) **Aviso vermelho falso ao tocar na notificação:** com o painel FECHADO o toque chega por dois caminhos quase juntos — a URL `?agendamento=ID` e a mensagem `notification-clicked` do service worker — e a mensagem podia chegar *antes* de os dados carregarem, mostrando "não encontrei esse agendamento" logo antes de os detalhes abrirem pelo outro caminho. `abrirAgendamentoDaNotificacao` (`js/admin.js`) agora espera `state.dadosCarregados`, guarda o pedido (`state.notificacaoPendenteId`) até o painel terminar de carregar, ignora o mesmo id repetido em 8 s e, antes de avisar que não existe, busca o documento direto no banco (a lista em tempo real pode ainda não ter o agendamento recém-criado). O aviso só aparece quando o agendamento de fato não existe — e então não abre os detalhes.

16. **Cliente fixo — horário que se repete toda semana (2026-11).** No "+ Novo agendamento" do painel, a caixa **"Cliente fixo"** cria uma *série* (`barbearias/{slug}/recorrencias/{id}`: cliente, profissional, serviços, dia da semana, horário, modo `mensal` | `ate`). Cada data vira um **agendamento normal** (`origem: 'dono-recorrente'`, `recorrenciaId`), então lembrete, notificação, concluir, cancelar e remarcar funcionam como sempre. **Renovação automática:** mantém agendado o mês corrente e, **a partir do dia 20, já gera o mês seguinte** (`DIA_RENOVACAO` em `api/_lib/recorrencia.js`). Quem renova: (1) rotina diária `api/cron-recorrencias.js` (Vercel Cron, `vercel.json` → `crons`, 09:00 UTC = 06:00 em Brasília, gratuito no Hobby) e (2) como reforço, o painel chama `renovar` ao abrir. Tudo é **idempotente**. Regras: data que já tem agendamento da série (mesmo cancelado) **não é recriada**; data sem vaga é **pulada e registrada** (e é tentada de novo nas renovações seguintes, se o horário vagar); cada data passa por `verificarSlot` dentro de transação; preço/duração são relidos do banco a cada geração (datas antigas não mudam); série "até uma data" se encerra sozinha; serviço/profissional removido gera `alerta` na série em vez de agendamento errado. API do dono: `api/recorrencia.js` (`previa`, `criar`, `listar`, `encerrar`, `renovar`); o botão "🔁 Horários fixos" na Agenda lista e encerra séries, e o detalhe de qualquer ocorrência tem "Encerrar horário fixo a partir desta data". **A rotina diária só roda se a variável de ambiente `CRON_SECRET` estiver configurada na Vercel** (sem ela, recusa tudo — nunca fica aberta); sem o cron, a renovação acontece quando o dono abre o painel. A coleção `recorrencias` não tem regra de leitura/escrita no Firestore: só o servidor (Admin SDK) acessa.

| Módulo | Arquivo | Resumo |

## Convenções ao propor mudanças

- Sempre seguir o padrão de nomenclatura e organização já existente antes de introduzir algo novo.
- Nenhuma função serverless deve confiar em dado de negócio (preço, destinatário, conteúdo de mensagem) vindo direto do corpo da requisição do cliente — buscar do banco via Admin SDK.
- Alterações em `firestore.rules` devem ser explicadas antes de aplicadas e sempre deployadas via `firebase deploy --only firestore:rules --project agendapro-179cb` — são sensíveis e afetam todos os negócios.
- Preferir soluções que continuem funcionando com git local + Claude Code.
- **`$$` (js/admin.js, app.js, painel77.js) devolve um Array**, nunca uma NodeList: `document.querySelectorAll(...).map/.filter/...` não existe e quebra EM SILÊNCIO dentro de um clique (o botão parece morto). `tests/estatico.test.js` falha se isso voltar. Ao simular handlers de tela em teste, use uma NodeList falsa (só `forEach`/`length`), não um array, senão o defeito passa despercebido.
